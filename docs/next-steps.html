1

Listing folders

eelisp-rs · src/editor.rs · done (eelisp-rs #29)

(dir-list "notes") returns one dict per entry, {:name :dir? :size :modified :ext}, and (file-info p) returns one. They sit beside notes and read-note, which follows the rule already in place: reading happens in the engine, writing goes through the app.

2

File operations as editor commands

eeditor-next · src/ui/keybindings.ts · src-tauri (fs_copy, fs_trash) · dev/bridge.mjs · done (#75)

(ed-move from to), (ed-copy from to), (ed-delete p) and (ed-mkdir p), handled beside write and append. Because they go through the app, open tabs stay in step: a moved note's tab follows it, and a deleted one closes. A delete goes to the system trash. They work from (bind …) lines and from forms alike.

3

Keys in a form

eeditor-next · src/ui/formrun.ts · src/core/form.ts · done (#76)

:on-key on the form, with :keys naming the keys it takes, receives each as $pressed in the notation (bind …) uses, such as "Mod-Left", and $control, before the app's own shortcuts. It fires outside text boxes only, since ⌘← in a text box means “go to the start of the line”. Listboxes and grids move their pick with the arrow keys, and Enter opens. After a form's file commands, its :on-refresh runs.

4

The form: workspace/examples/Files.eeform

eeditor-next · workspace/examples/Files.eeform · in the manual, the welcome note and on the home page · done (#77–#81)

Two grids, a path over each, a status line. Tab switches panel, Enter opens, ⌘→ / ⌘← move the selection to the other panel, ⌥⌘→ / ⌥⌘← copy it, ⌘⌫ sends it to the trash.

(defn fm-key (f key)
  (cond (= key "Mod-Right") (fm-transfer f "left" "right" ed-move)
        (= key "Mod-Left")  (fm-transfer f "right" "left" ed-move)
        (= key "Tab")       (fm-swap-focus f)))
5

Folders outside the workspace

both repos · done (eelisp-rs #31) — named roots, ~Downloads/…

Engine and app keep every path inside the workspace today. A file manager wants ~/Downloads too, so the user grants extra folders, the way Open With already grants single files. On macOS the first read of a protected folder waits for the privacy dialog, so these calls run asynchronously and never on the main thread.

Part 3 · Shipping it as its own app

An exported page can't touch files today. The WebAssembly engine connects no filesystem, and the exported runtime ignores ui-editor commands.

Built · Mac

Desktop export

A small app that opens one form as its main window, with no editor, using the native engine and file commands. It has full power.

Export as Mac app… copies EEditor, puts the form's app inside it, renames it, gives it an identifier and a data folder of its own, and signs it ad hoc on the spot, so nothing has to be compiled. The copy opens the form at the form's size, and the form fills the window. A file manager starts at the home folder. Windows and Linux would carry the app beside the program in the same way; that isn't built yet.

src-tauri/src/lib.rs (export_mac_app, hosted) · src/runtime.ts · src/ui/appcommands.ts
Extra

Web export with folder access

The page asks for a folder, then lists, reads and writes it in the browser. It only works in Chrome and Edge, not in Safari or Firefox. With no native rename, a move is a copy followed by a delete.

Either way, steps 1 and 2 go through one small file interface (list, read, write, move, copy, delete) that the editor and the exported runtime both implement. Exporting then means plugging in another implementation, not rewriting the app. It also keeps the file browser self-contained if it later becomes a project of its own.
